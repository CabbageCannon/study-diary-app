# 多对话任务书

版本：2026-09-06。产品经理负责需求、依赖和最终验收；客户只需要指派角色、选择视觉方向并进行手机实机试用。以下任务尚未创建为独立对话，也尚未由任何角色执行。

## 共同工作规则

1. 先读本目录 `README.md`、`demo-review.md` 和本任务书。当前工作区是需求来源，已提交旧版本不能取代当前 demo。不得自动丢弃、覆盖或打包提交别人尚未核实的修改。
2. 所有功能分支从 M0 公布的统一基线开始，使用独立 worktree/工作目录。当前主工作区保持原样。设计和内容准备可以先开始，功能编码等待基线。
3. 每个角色只改自己拥有的文件。跨边界需要把请求写入交付报告，由产品经理协调，不能顺手重写其他模块。
4. 客户授权完成后自行上传 GitHub。仓库是 `CabbageCannon/study-diary-app`；每人提交自己的 `codex/mobile-*` 分支并创建 PR。只暂存本任务文件，先检查暂存差异；不使用盲目的 `git add .`，不强推共享分支，不自行合并默认分支。
5. PR 基准使用 M0 公布的集成分支，不能猜成 `main`。评估时 GitHub 默认分支是 `feat/study-diary-mvp`。若客户尚未指派集成人，应交付分支和 draft PR，说明依赖。
6. `.env`、模型密钥、SQLite、真实回答/日记、浏览器存储和包含个人数据的截图不上传公开仓库。测试样例使用原创、虚构练习内容。不得为测试改写客户题库和训练历史。
7. 自用范围：不做多租户、RBAC、注册系统、复杂队列、分布式限流或商业化设施。仍要保护草稿和已有记录，模型密钥留在后端。
8. 每个任务交付：分支名、commit SHA、PR 链接、做了什么、实际跑过的检查及结果、截图/样例、已知限制、下游接口变化。失败不能写成通过；尚未进行的真机验收单独列出。
9. 发生阻塞先完成能独立完成的部分，再报告具体阻塞；不得自行扩大产品范围或改技术栈。完成一阶段后先推送可检查的提交，不把“已经写代码”当作已交付。

## 角色、边界与依赖

| 角色 | 主要交付 | 文件所有权 | 依赖 |
| --- | --- | --- | --- |
| A 视觉与交互 | 五个关键屏幕、状态设计、统一规范 | `docs/mobile-app/design/`；选定的导出资源放该目录。正式 `frontend/public` 资源由 B 导入 | 可先开工；参考当前 demo；实现前客户选方向 |
| B 移动端前端 | 首页/导航、八股、算法思路与核对、复习/我的 | `frontend/src/**`、业务静态资源 `frontend/public/**`，不含 PWA 图标/平台配置 | M0 + A 选定规范 + C 接口协议 |
| C 后端与 LLM | 题目上下文、核对协议、持久化与重试、评估样例 | `backend/app/**`、`backend/alembic/**`、业务测试与导入器；`docs/mobile-app/api/` | 可先设计协议；编码依赖 M0；内容字段先和 D 对齐 |
| D 题库内容 | 完整可读题意、核对依据、原创反例与参考点 | `backend/data/mobile/**`、`docs/mobile-app/content/`；不直接改数据库/schema | 可先制作少量样例；全量按 C 冻结的协议填写 |
| E 集成、PWA 与验收 | M0 基线、集成分支、构建发布、iPhone 验收 | 工程配置、依赖文件、PWA 配置/图标、部署文档、专门的端到端验证资料 | M0 先行；后续等待 B/C/D，再集成和部署 |

`frontend/src` 公共导航、全局样式和共享输入组件只由 B 修改。`backend/app/schemas.py`、`models.py`、`prompts.py` 只由 C 修改。依赖清单、锁文件、Vite/PWA 配置由 E 修改；B/C 提供依赖需求。E 集成冲突时保留实现方的业务判断，需要业务修改先返回对应负责人。M0 是对现有改动的整理例外，不授权 E 大范围重写业务。

## 给 A 的完整指派词

> 你是这个项目的视觉与交互设计负责人。请先读 `docs/mobile-app/README.md`、`demo-review.md` 和 `TASKS.md`。客户个人用 iPhone 刷八股、口述算法思路并让 LLM 核对，要求简洁优雅、有 ins 感，避免 AI 风格和后台式界面。基于当前 demo 提出两种克制的视觉方向，优先比较当前浅绿的延续与暖白纸张感；交付大尺寸、可看清中文的手机稿，不用小缩略图拼板代替页面。关键页面为今日、八股作答、算法作答、核对反馈、复习列表，并提供键盘展开、核对中、失败重试、无内容的设计。若使用的设计技能要求不同数量的探索方案，以已加载技能为准，但最终只保留一套客户选定规范。不得独自改正式业务前端。所有工作放 `docs/mobile-app/design/`，包括颜色、字体、尺寸、间距、组件和交互说明。先推送可审阅的探索分支和 draft PR，等客户选定后补齐规范并更新 PR。按任务书 GitHub 规则交付 `codex/mobile-design`。

验收：五屏一致；主要操作首屏可达；中文可读；题目与回答高于统计；图稿里可见失败和键盘状态；规范足够让 B 不再自行猜设计。

## 给 B 的完整指派词

验收：390/428 宽正常，375 宽可用；开始不超过两次点击；主要按钮不被键盘遮挡；长题意可滚动且不误切题；修改回答不会沿用旧反馈；原有日记/历史仍可达。

## 给 C 的完整指派词

> 你是后端与 LLM 负责人。先读产品提案、demo-review 和任务书，检查现有算法/八股服务与持久化。优先设计一个有可信题目上下文的“思路核对”协议：题意、输入输出、约束、示例、核对要点、来源版本、用户回答一起进入核对；不要仅凭题名猜测。输出至少包括结论、正确部分、需补充/错误点、必要反例或追问、复杂度、上下文是否充分。认可多种有效解法，不要求写代码，不将含糊表述直接判错，不声称在线判题通过。优先复用现有训练、尝试和复习模型；设计并实现回答保存与评估分离、失败重试不重复保存、反馈与回答版本关联。接口在 `docs/mobile-app/api/` 给出完整成功/信息不足/失败样例，先与 B/D 对齐，再编码。题库数据正文由 D 维护；你维护 schema、导入器、迁移和服务。对正确解法、关键错误、缺边界、错误复杂度、不同正确方案、含糊回答、缺题意、恶意要求模型直接给满分、模型超时和无效输出建立精简但有区分力的评估集。mock 验证与真实模型核对结果分开报告。保持个人 SQLite 使用，不扩展多用户或高并发设施。完成后自行上传 `codex/mobile-reasoning` 并创建 PR，附真实运行过的检查。

验收：一次点击形成可靠保存与核对；重复重试不重复记录；补充回答后反馈有正确关联；上下文不足会追问；现有记录兼容；固定样例显示具体反馈而非空洞鼓励。

## 给 D 的完整指派词

## 启动顺序与回报

第一批：E 整理 M0；A 做视觉；C 起草接口；D 制作题目样例。这些任务边界清楚，可以在不同对话中同时推进。第二批：M0 与设计/协议确定后，B 开始正式实现，C/D 扩展。第三批：E 集成，一条完整练题链路通过后再验全应用。

各对话交付 PR 后，产品经理读差异和检查证据，安排修正、依赖更新和集成；不是仅凭“完成”二字验收。新任务尚未创建时不会自动运行，客户需要把相应指派词发给对应对话。
